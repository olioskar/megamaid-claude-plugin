# Phase 2: usage ledger — design

Date: 2026-10-18. Phase 2 of `docs/handover/plan.md` (idea C10 of the ideation spec). Revision 2 (amended after the branch review: two wording fixes, one live assumption added), after one two-lens review (`docs/megamaid/reviews/2026-10-18-phase2-spec-review.md`; the code lens built rev 1 in a scratch copy and every free gate passed, 46 tests). Written in an unattended session: the maintainer asked for the phase to be carried on without them ("get this done") and ruled out eval runs in this session, so every decision below is the implementer's call unless it cites the plan or an earlier decision. The maintainer reviews the result, not the design.

## Goal

The hooks module records what each megamaid run costs, per role, from `turn.complete`, and writes it to a file the maintainer can read after the run: the usage ledger. One ordinary full loop then gives the orchestrator-to-subagent split that plan.md Phase 2 asks for, the bar every later phase is measured against, and the number that decides Phase 6.

## Why

- The ideation spec's token estimate (orchestrator 20–35%) is unmeasured. Phases 3 to 6 are justified by orchestrator savings; if the orchestrator is under 20% only Phase 6 is worth doing for tokens.
- The eval suite reports cost per case, not per role; a kept trace has per-call usage but no attribution to lane and role. The module already records every dispatch of a run with its lane and role (Phase 1), so attribution is a lookup.
- `turn.complete` carries the four token counts and the model per loop (main loop and each subagent), and `$.session.usage().cost.usd` gives the session's running cost, so the ledger needs no price table.

## Bound

- **What is counted.** Every `turn.complete` that carries `usage`, while a run is stored: a main-loop turn (`agentId` absent) goes to the orchestrator; a turn whose `agentId` is a recorded agent of the run goes to that agent; every other turn (an agent megamaid did not dispatch, a turn with no stored run) counts nowhere and writes nothing. A turn without `usage` (interrupted before a request, an API error) adds nothing, not even to the turn count. A run stored before 0.4.0 (a 0.3.x run across a hot reload) has no `usage` and is left uncounted until the next run. A hook that fails is replayed beneath and named in the debug log (`usage hook failed: <message>`; nothing under re-entry, where `$` calls reject).
- **Run end.** A run ends when the next run starts (`skill.prompt` of a run skill) or the session ends (`/clear` included). There is no earlier signal the module can trust: a main-loop turn that ends on text is a question as often as it is the run's last answer (review's scope question, fix's dirty-tree pre-flight, vacu-suck's "run again?"), and a background agent's completion raises a main-loop turn of its own. So main-loop turns between the run's last answer and the next run or session end are counted as the orchestrator's; the ledger shows the orchestrator's turn count and the time of the last counted turn, which makes the overrun visible. The stored run stays "the last run, not an active one" (Phase 1).
- **A sweep's "run again".** vacu-suck's second round starts from review inside the same skill invocation: no new `skill.prompt`, so it is the same run. Its ledger stays where the first report put it and its totals cover every round; the round-2 report's Write does not move it (`report` is set once). The `Run:` line's start time shows the span. The baseline loop answers "no" to "run again?", so its ledger is one round.
- **Nested agents.** A spawn raised inside a recorded agent (`parentAgentId` is a recorded agent's id) is recorded under the parent's lane, role and stem, with its own `subagentType` and `provider` and a `parent` field, so a reviewer's helper agents count toward the reviewer's role. Every role but the two writers may spawn (their frontmatter withholds Write, Edit and NotebookEdit only; planner and implementer withhold Agent). A brief path inside a nested prompt is not parsed: the parent's key stands. A spawn nested in an unrecorded agent is ignored, as today. Not verified live: that the engine raises `agent.spawn` for a subagent's spawn to this plugin's hook; the types say it does (`parentAgentId`, and `turn.complete` is heard for every agent). If it does not, the nested usage is missing from the split and the ledger under-counts the subagent side; the first live loop shows it (an agent row whose `Agents` count is lower than the trace's Agent calls). Also unverified live: an agent whose turn ends before its spawn record lands (the spawn hook's state write against the agent's first API call) counts nowhere; a row whose `Turns` is below its `Agents` shows it.
- **Where the ledger goes.** A run of `megamaid:review` or `megamaid:vacu-suck` writes it beside the review report, `<…>-usage.md` next to `<…>-report.md`, once the report exists, and rewrites it after every counted turn from then on; before the report exists nothing is written to disk (the counts are in `$.state`), and a review or sweep that ends without a report leaves no ledger file. Every other run, the synthetic `none` run included (a brief spawn with no stored run, `hooks/agents.ts`), writes `.megamaid/usage/<skill>-<startedAt>.md` after every counted turn (`none-<startedAt>.md` for that case; its cost line reads unavailable, since the run's start was never seen). `.megamaid/` ignores itself in git (`megamaid.py` and `manifest.py` write `.megamaid/.gitignore` with `*`); the hook writes the same file first when it is missing, so the usage folder never shows in `git status`. `manifest.py clean` removes `excerpts/<stem>*` only, so ledgers under `.megamaid/usage/` stay after the run (the README sentence saying `.megamaid/` is cleaned at the end of each run is amended). A ledger beside the report is tracked with the report, so a fix run's per-item commits do not pick it up by accident: fix stages the implementer's files by name (`git add <files reported by implementer>`). Why beside the report at all, when `.megamaid/usage/` for every run would give the same number with one hook: plan.md names the place, and the review report is where the maintainer reads a run's outcome; the cost is one observer hook, one basename test and one state field.
- **How the report is found.** The main loop's `tool.call` of `Write` during a review or sweep run whose `file_path` basename is `megamaid.py report-name`'s shape, `^(pr-\d+|branch-.+)-round\d+-report\.md$` (either separator), and whose result is neither denied nor an error. The first such Write sets the run's `report`; later ones leave it. A Write from a subagent is ignored. Assumption: the orchestrator writes the report with the Write tool. Review Step 8 says "the path to write" and the skill allows Bash and Edit too; a report produced by a shell heredoc or assembled with Edit raises no `tool.call{tool=Write}`, and the ledger never lands. The replay fixture's sweep and every kept eval trace used Write; the first live loop confirms it. No prose pin is added (Phase 2 changes no skill text); if the live loop shows the gap, Step 8 gains one sentence in a later change.
- **Cost.** The ledger's cost line is `$.session.usage().cost.usd` at the last counted turn minus the same at run start: the session's whole spend over that interval, including anything that is not the run. When `$.session.usage` fails or carries no `cost` at either end, the line says the cost is unavailable; the token rows stand. Per-role cost needs a price table and is not in this phase.
- **Shares.** The split is reported twice, as the orchestrator's share of input tokens (uncached + cache read + cache write) and of output tokens. The two price classes differ by an order of magnitude, so one blended number would need prices. A reader with prices can weight the rows.
- **No prose changes.** No skill, shared block, agent file or script changes. The graders that key on the skills' templates are untouched. Phase 2 adds no config key: the ledger has no knob (it is a measurement, not a behaviour).
- **Observers refuse nothing.** Both new hooks (`turn.complete`, `tool.call{tool=Write}`) await `next(e)` first, return its result by reference, and take the pass-through `.catch(($, e, next) => next(e))`. A fault means a missing or stale ledger, never a refused Write or a changed answer. validate lists `tool.call{tool=Write}` as a gating hook with .catch and `turn.complete` among the hooks (not as gating: a failed `turn.complete` hook leaves the answer as it was); `tsc` and the tests cover it either way.
- **Eval run.** None in this session (maintainer, 2026-10-18). The suite gains two graders that a later run verifies; the handover names them as unverified, with these assumptions behind the `plan-native-planner` one: that `$.fs.write('.megamaid/usage/…')` resolves against the eval sandbox's workspace (the types say the session's working directory; the spike recorded only that an absolute `$.fs.write` reached outside the sandbox), and that the eval's `file_exists` glob matches a dot-directory (the offline replay does, through Python's `glob`). If either fails live, the grader is dropped and the unit tests stand.

## Decisions

| Question | Decision |
|---|---|
| Key | Usage is kept per agent (`agents[id].usage`) and for the main loop (`run.usage`); the ledger sums per key. `usageKey(agent)` is `lane === null ? subagentType : lane + '/' + role`: `review/code-reviewer`, `fix/implementer`, and for the briefless patterns scanner and shaver `megamaid:pattern-scanner`; a spawn nested under a briefless agent keys on its own `subagentType`. The main loop's key is `orchestrator`. Keying by (lane, role) is what Phase 1 planned; the per-agent store is what a Phase 5 pane needs, and the sum is a fold. |
| Usage shape | `{ turns, input, cacheRead, cacheWrite, output, model }`: the four API counts under short names, the turn count, and the model of the last turn that counted (`TurnUsage.model`, the API's id). Summed per loop over its turns. |
| Run fields | `MegamaidRun` gains `usage` (the orchestrator's, zero at start), `report: string | null`, `costAtStart: number | null`, `lastTurnAt: number | null`. `MegamaidAgent` gains `usage: MegamaidUsage | null` (null until its turn ends) and `parent: string | null`. |
| Attribution site | One `turn.complete` hook in `hooks/usage.ts`: `await next(e)`; if `e.usage` is absent, return; `$.state.get(RUN)`; if no run is stored, or `e.agentId` is set and is not a recorded agent, return (nothing is written); then `update($, RUN, fn)` adds the turn to the orchestrator or the agent and sets `lastTurnAt` from `$.clock.now()`; then the ledger is rendered and written when it has a place; then the debug log gets `usage <key> +<input>/<output> (<turns>)`, `<input>` the turn's three input counts summed. The read before the update is the same shape as `hooks/agents.ts`'s; a run starting between the read and the update attributes one turn to the new run, which is harmless. Two agents ending at once may write the ledger out of order; the last writer wins until the next main-loop turn, which always ends last. |
| Report site | One `tool.call` hook with matcher `{ tool: 'Write' }` in `hooks/usage.ts`, main loop only, result neither denied nor errored, stored run's skill in `REPORT_SKILLS = ['megamaid:review', 'megamaid:vacu-suck']`, `report` still null, basename matching `REPORT_NAME`; sets `run.report` to `e.file_path` as given and writes the ledger at once (the report's Write is a step inside a main-loop turn, not a turn; the ledger then exists before the run's next turn ends). |
| Ledger path | Beside the report: `report` with `-report.md` replaced by `-usage.md`. Otherwise `.megamaid/usage/<skill>-<startedAt>.md` with `<skill>` the name after `megamaid:` (`plan`, `fix`; `none` for the synthetic run); the path is relative to the working directory, which `$.fs.write` resolves. Decided over learning `paths.reviews` from the skill's `megamaid.py config` call (parsing a tool result) and over watching the plan and fix lanes' Reads for a report path (two heuristics for two lanes): the review report is the one artifact every lane keys off, and the plan and fix ledgers under `.megamaid/` are a working-file location the plugin already owns. |
| Ledger format | Markdown, rewritten whole from state on every write; nothing is appended. Exact lines: title `# megamaid usage: <skill>` (the qualified skill, `megamaid:vacu-suck`); `Run: started <ISO>, last turn <ISO> (UTC)` (`none yet` for the last turn before one counted); `Cost: <usd> USD (session spend from run start to the last counted turn; includes anything else in the session meanwhile)` with two decimals, or `Cost: unavailable (no session cost at run start or now)`; one table `| Lane/role | Agents | Turns | Input | Cache read | Cache write | Output | Model |` with the orchestrator first (`Agents` cell `-`), agent keys in spawn order (`seq`, stamped per agent by `addAgent`: `Object.values` would put an all-digit id first), and a `total` row (agents counted, counts summed, `Model` empty); then `Orchestrator share: <N>% of input tokens, <M>% of output tokens.` Numbers are plain integers (no locale); a percent is rounded to the nearest integer and a zero total gives `0%`. A row's `Model` is the distinct last-turn models of the loops summed under that key, comma-joined in first-seen order (a loop that changed model mid-run shows its last). |
| Cost at start | Read in the `skill.prompt` hook when the run starts, inside its `try`, with `$.session.usage().catch(() => undefined)` so a missing answer (the test kit, a host with no cost ledger) leaves `costAtStart` null and the run still starts. |
| Pure code | `hooks/ledger.ts` holds the pure helpers (no `$`): `ZERO`, `addUsage`, `usageKey`, `reportName`, `ledgerPath`, `renderLedger`, `REPORT_SKILLS`, `REPORT_NAME`. `hooks/run.ts` keeps run detection and imports `ZERO` from `ledger.ts` for `startRun` (no cycle: `ledger.ts` imports types only). `startRun` and `addAgent` grow the new fields. The PLAYBOOK's "Where things live" names `ledger.ts`. |
| RUN const | `hooks/usage.ts` declares its own `const RUN`, as every file that writes state does; check-contract §12's list of RUN files gains it. |
| Report-name shape, two sources | `REPORT_NAME` in `ledger.ts` repeats `megamaid.py report-name`'s shape in a second language, deliberately. check-contract keeps them equal: it extracts the pattern from `ledger.ts` with `sed` (as §11 extracts the stop line) and tests it against the `report:` basenames `megamaid.py report-name` prints for a `--pr` and a `--branch` case in an empty folder. |
| Version | 0.4.0: a new artifact users see, pre-1.0 minor. |

## Changes

### Types: `types/index.d.ts`

```ts
export type MegamaidUsage = { turns: number; input: number; cacheRead: number; cacheWrite: number; output: number; model: string | null }
export type MegamaidAgent = { subagentType: string; provider: string; role: string; lane: string | null; runStem: string | null; parent: string | null; seq: number; usage: MegamaidUsage | null }
export type MegamaidRun = { id: string; skill: string; startedAt: number; agents: Record<string, MegamaidAgent>; usage: MegamaidUsage; report: string | null; costAtStart: number | null; lastTurnAt: number | null }
```

### Hooks

- `hooks/run.ts`: `startRun(id, skill, startedAt, costAtStart = null)` fills the new fields (`usage: ZERO`, `report`, `lastTurnAt` null). `addAgent(run, agentId, agent: Omit<MegamaidAgent, 'seq'>)` stamps `seq` (the spawn order within the run); callers pass the two new agent fields.
- `hooks/ledger.ts` (new, pure): as in Decisions. `reportName(path)` tests the basename after the last `/` or `\` against `REPORT_NAME`. `ledgerPath(run)` returns beside-the-report for a `REPORT_SKILLS` run with a report, null for one without, and `.megamaid/usage/<skill>-<startedAt>.md` for every other skill. `renderLedger(run, costNow: number | null)`.
- `hooks/usage.ts` (new): `registerUsage(on)` with the two hooks above, and `writeLedger($, run)`: resolves the path; when null returns; when the path starts with `.megamaid/`, writes `.megamaid/.gitignore` (`*\n`) first if `$.fs.exists` says it is missing; reads `$.session.usage()` for the cost (tolerant, as at start); writes the rendered text; logs `ledger <path>` on every write and `ledger failed: <message>` from its own `catch` (a failed write must not fail the hook's state update, which already landed).
- `hooks/agents.ts`: the early return on `e.parentAgentId !== undefined` becomes: when the parent is a recorded agent of the stored run, record the spawn with the parent's `role`, `lane`, `runStem` and `parent: e.parentAgentId`, no brief parsing; otherwise return as today. The log line for a nested spawn reads `<lane>/<role> nested spawn <subagentType> (<agentId>) under <parent>`.
- `hooks/skill-prompt.ts`: reads `costAtStart` as decided and passes it to `startRun`.
- `hooks/register.ts`: `registerUsage(on)` after `registerAgents`.
- `hooks/test-rig.ts`: `rig(on, { clock?, usage? })` gains: an ordered `fsWrites: [path, text][]` recorder on `fs.write` (answering `{ value: undefined }`, or `{ deny }` while `rig.failWrites` is set), an `fs.exists` answer (false unless the test adds the path to `rig.existing`), a `session.usage` answer whose `cost.usd` is `rig.cost` (default 3.5; withheld with `usage: false`), and a `turn.complete` answer `({ text: e.answer })`. The kit resolves a relative `fs.write` or `fs.exists` path against the test session's cwd (the plugin folder) before a test hook sees it; the recorder strips everything before `/.megamaid/` so tests match the relative spelling. `turnInput(over)` builds a `TurnCompleteInput` (`reason: 'answer'`, a `usage` of four counts and a model; a cast is needed over the refused/unrefused union).

### Tests (`hooks/usage.test.ts`, `hooks/ledger.test.ts`, `hooks/agents.test.ts`)

Each written first and seen to fail; a negative test carries a positive control.

- A main-loop turn during a run adds to the orchestrator (turns, four counts, model); with no stored run nothing is written (control: after a skill prompt, it is).
- A recorded agent's turn adds to that agent; an unrecorded `agentId` adds nothing (control in the same body); two turns of one agent sum.
- A turn without `usage` writes no state (control: with usage it does).
- A plan run writes `.megamaid/usage/plan-<startedAt>.md` after a main-loop turn, and `.megamaid/.gitignore` first when `fs.exists` says it is missing (control: when it exists, no second write of it; the ordered recorder proves the count).
- A review run writes no file before its report; after a main-loop Write of `<dir>/branch-x-round1-report.md` the ledger is at `<dir>/branch-x-round1-usage.md` and is rewritten after the next turn; a second report Write leaves `report` as it was; a Write of a file not named like a report, a subagent's Write of a report name, and a denied Write set no report (controls).
- The cost line: `costAtStart` 1.00 and `session.usage` now 3.50 gives `Cost: 2.50 USD …`; with `session.usage` withheld the run still starts (`costAtStart` null) and the line says unavailable.
- A nested spawn under a recorded agent is recorded with the parent's lane, role and stem and `parent`; a brief path in the nested prompt does not re-key it; under an unrecorded parent it is ignored (the existing test gains these controls); the nested agent's turn counts under the parent's key in the ledger.
- `renderLedger`: the table has the orchestrator first, keys in spawn order (an all-digit id keeps its place), a `total` row, and the two shares; a percent rounds to the nearest integer; zero totals give `0%`; a briefless agent's key is its `subagentType`; a `none` run's path is `.megamaid/usage/none-<startedAt>.md`; two agents under one key with different models render both.
- `usage.ts` guards pinned directly: a denied `state.get` logs `usage hook failed: …` and the turn still answers; a run stored without `usage` leaves no state write, no file and no hook failure; two report Writes landing together leave one `report` and one ledger place (the update's `run.report ?? path`, seen to fail without it).
- Isolation: an `fs.write` the test denies leaves the state write standing and logs a line starting `ledger failed: `.

## Not in this phase

- Per-role cost in USD (needs a price table).
- A run end earlier than the next run or session end.
- A ledger for a review or sweep interrupted before its report; a per-round ledger inside one sweep.
- Showing usage in the UI (Phase 5).
- Reading `paths.reviews` or `paths.plans` in the module.
